# Задача 12.4 — «Рішення про власний харнес»

## Мій робочий кейс

У своїй роботі я використовую Copilot для задач. Наприклад, чому прогрес степера не оновлюється після створення нового елементу. Під час дослідження з’ясувалося, що треба перевірити не лише місце створення: причиною були відсутні події оновлення і відписки компонентів, які видаляли чужих слухачів. Я уточнював межі виправлення, сценарії часткового успіху, видалення та тестування, а після цього просив оновити план.

Інша задача: коли фільтр приховує контент кількох колонок в таблиці, текст іншої колонки, що лишається має займати звільнений простір. Це дільш типова для мене задача: агент читає реальний код і правила репозиторію, досліджує кілька варіантів, ставить уточнювальні питання, готує план, а я спрямовую роботу й вирішую, чи переходити до реалізації.

## Рівень, який я обираю

Для цих сценаріїв мені потрібен **готовий інтерактивний харнес Claude Code у репозиторії**. Він відповідає моєму циклу роботи: дослідити код і тікет, пройти уточнення, скласти план, отримати моє схвалення, реалізувати зміни й перевірити їх. Проєктні інструкції, дозволи, хуки, субагенти та доступ до Git мають діяти в цьому ж середовищі. Для одноразового автоматизованого кроку можна розглянути `claude -p`; якщо агент стане частиною власного сервісу, тоді оцінити Agent SDK.

Це оцінка того, як я б переніс ті самі сценарії на Claude, а не результат фактичного повторного запуску Claude на робочому репозиторії.

## Що довелося б відтворити на третьому рівні

Якщо я обрав би Messages API та власний агентний цикл, мені довелося б самостійно реалізувати:

- **Робочий цикл і інструменти:** читання та пошук у коді, безпечне виконання команд, обробку tool calls, результатів, помилок і повторів.
- **Стан роботи:** історію діалогу, потрібний контекст тікета й репозиторію, межі контекстного вікна та відновлення після перерви.
- **Мої правила процесу:** уточнення вимог до плану, паузу до мого схвалення, дозволи на зміни, Git-огляд, запуск релевантних перевірок і блокування завершення, якщо незалежний oracle не пройшов.
- **Операційний контроль:** облік токенів і вартості, бюджет ходів, тайм-аути та журналювання.

## Три ризики третього рівня

1. **Безпека.** Помилка у власному виконанні інструментів може надати вмісту тікета або репозиторію вплив на файлові чи мережеві дії; дозволи й захист секретів тоді повністю на мені.
2. **Надійність.** Помилки в циклі інструментів або відновленні сесії можуть втратити рішення з обговорення, повторити зміну чи пропустити крок схвалення.
3. **Якість і вартість супроводу.** Якщо неповно відтворити правила, хуки та перевірки, задачі можуть завершитися планом без перевіреної поведінки, або зміною лише частини з потрібних файлів. Підтримка власного харнесу також потребуватиме тестів і адаптацій до змін API.

## Рішення

Я залишаюся на інтерактивному Claude Code. Він дає потрібний мені контроль над дослідженням, планом і реалізацією без створення ще одного сервісу та відтворення інструментів. До власного SDK або циклу на Messages API я перейду лише тоді, коли ті самі задачі потрібно буде запускати автоматично у сервісі чи CI з централізованими правилами.
